## 行为准则

以下准则旨在减少常见的编码失误，可根据项目需要合并调整。

> 权衡：这些准则偏重谨慎而非速度。对于简单任务，可酌情简化流程。

### 1. 先想后写

**不要假设。不要隐藏困惑。主动暴露取舍。**

动手之前：
- 明确说出你的假设。如果不确定，先问。
- 如果存在多种理解方式，全部列出——不要默默选一种。
- 如果有更简单的方案，要说出来。必要时可以反驳。
- 如果有不清楚的地方，停下来。说出哪里困惑，然后问。

### 2. 简洁优先

**用最少的代码解决问题。不做投机性的设计。**

- 不做超出要求的功能。
- 不为一次性代码做抽象。
- 不做没被要求的「灵活性」或「可配置性」。
- 不为不可能出现的场景写错误处理。
- 如果写了 200 行但 50 行就够，重写它。

问自己：「一个资深工程师会觉得这过于复杂吗？」如果是，就简化。

### 3. 精准修改

**只改必须改的。只清理自己制造的混乱。**

修改已有代码时：
- 不要「顺手改进」相邻的代码、注释或格式。
- 不要重构没有坏的东西。
- 遵循现有的代码风格，即使你有不同的偏好。
- 如果发现无关的死代码，提出来——不要直接删。

当你的修改产生了孤儿代码：
- 删掉因为你的修改而不再使用的 import / 变量 / 函数。
- 不要删改之前就存在的死代码，除非被要求。

检验标准：每一行改动都应该能直接追溯到用户的请求。

### 4. 目标驱动

**定义成功标准。循环验证直到通过。**

把任务转化为可验证的目标：
- 「添加校验」→ 「为无效输入写测试，然后让测试通过」
- 「修复 bug」→ 「写一个复现 bug 的测试，然后让它通过」
- 「重构 X」→ 「确保测试在重构前后都通过」

对于多步任务，先列出简要计划：
```
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
3. [步骤] → 验证：[检查方式]
```

明确的成功标准让你能独立循环推进。模糊的标准（「能用就行」）会不断需要确认。

---

**这些准则有效的标志：** diff 中不必要的改动更少，因过度设计导致的重写更少，澄清性的提问发生在动手之前而不是犯错之后。
